# 这套语法的扩展能力：边界与路线

先给结论：**它的扩展空间很大，但真正的杠杆点只有一个——语句生命周期的拦截层。其余方向要么收益递减，要么会把 SQL 重新藏起来。**

下面拆开说。

---

## 一、先看清它到底是什么

这套格式的价值不来自"用 JSON 存 SQL"，而来自三个性质：

| 性质 | 含义 | 由此解锁的能力 |
|---|---|---|
| **可寻址** | 每条语句有稳定 id（`user.findPage`） | 引用、覆盖、审计、监控、灰度 |
| **可组合** | template + vars + 追加 sql | 继承、分层、局部覆盖 |
| **描述是数据** | `params` 是结构化字段，不是注释 | 编译期校验、代码生成、契约 |

第三条是分水岭。MyBatis 的 XML 同样可寻址、可组合，但它的类型信息散落在 Java 侧和约定里，所以只能做到"模板复用"，做不到"编译期校验"和"从定义生成代码"。

**这套语法真正比 XML 多的，就是第三条。**

---

## 二、四个扩展方向

用一个坐标看：

```
                横向（语句之间）
                       │
  内向（类型/元数据）──┼── 外向（跨实体）
                       │
                纵向（生命周期）
```

### 方向 A：横向组合 —— 边际收益递减

已有 `template` + `vars` + 语句追加。还能加：片段 `@include`、多级继承、条件片段。

**但这条路很快就到顶。** SQL 的组合需求远小于代码：超过三层的语句继承，人已经无法在脑里展开，读的人必须跳三个文件才能知道最终 SQL 长什么样——这直接违背了"SQL 一眼可读"的初衷。

评估：**做到片段复用就该停。**

### 方向 B：纵向生命周期 —— 唯一的高杠杆点

这是我最看重的方向。一次实现，**所有语句自动受益**，业务代码零改动。

插入点：

```
load → [编译前] → prepare → [SQL 重写] → [执行前] → JDBC → [结果后]
```

四个高价值用法，按价值排：

| 用法 | 做什么 | 为什么值 |
|---|---|---|
| **多租户注入** | 所有查询自动加 `tenant_id = ?` | 业务代码不用写、不会漏、改不坏 |
| **软删除过滤** | 自动加 `deleted = 0`，delete 改写成 update | 同样的"不会漏" |
| **全表操作拦截** | 无 where 的 update/delete 直接拒绝 | 一次上线，永久防呆 |
| **方言转换** | `LIMIT ?` → `ROWNUM` / `OFFSET FETCH` | 换库不用改 200 条语句 |

技术上已经具备条件：我们在 `SqlV2` 里已经有 `detectRegions()`（识别 INSERT 列区/值区、UPDATE 的 SET 区），这正是做 SQL 重写所需的"轻量结构识别"。

**不需要完整 AST。** 用规则 + 约束就能覆盖 90%：要求 where 必须写成 `WHERE 1=1` 锚点，重写时只需在锚点后追加，风险可控。

### 方向 C：内向类型系统 —— 低成本、高回报

`params` 已经是数据了，往下走三步都很便宜：

1. **编译期校验**：`#n` 编号连续、每个 `#n` 都有描述、`{{var}}` 有定义、`ident/raw` 位置有清单 → 进 CI
2. **代码生成**：从 JSON 生成 `UserSql.FIND_PAGE = "user.findPage"`，把字符串变成编译期符号，改错名字编译就报错
3. **快照测试**：每条语句的 `(sql, args)` 存 golden file，改一行 SQL 立刻看到 diff

这三件事加起来不到两天，但能把"运行时才发现"的问题全部前移到 CI。

### 方向 D：外向跨实体 —— 价值高，但复杂度陡增

- **关联查询**：只做"一次 join 查出扁平结果 + 手动组装"，**不要做对象图**（懒加载、级联、脏检查）。后者是 Hibernate 走过的路，复杂度指数上升。
- **分库分表**：`t_order_{{shard}}` —— 编译期变量天然支持，路由在仓库层决定。这是 `{{}}` 最自然的延伸，值得做。
- **批量**：`#{items.tuples}` 已有，缺的是 `UPDATE ... CASE WHEN` 批量更新，收益一般。

---

## 三、边界：三条红线

这套语法最大的风险不是功能不够，而是**功能加多了，它就不再是它**。

1. **任何让 SQL 不再"一眼可读"的能力，不做。**
   这是它存在的唯一理由。一旦要跳三个文件才能还原最终 SQL，它就和 MyBatis XML 没区别了。

2. **不做对象图 ORM。**
   懒加载、级联保存、脏检查、一级二级缓存——每一样都能做，但每一样都在把"看得见的 SQL"换成"猜得到的魔法"。

3. **不做运行时拼装 API。**
   `where().and("age", ">", 18).or(...)` 这种链式 DSL，会让 SQL 彻底消失在代码里，等于退回 MyBatis 之前。

判断标准可以压成一句话：

> **新增能力是让 SQL 更容易被看见，还是更容易被隐藏？**

前者做，后者不做。

## 四、路线图

### Stage 1 · 基础（1–2 天，事务已完成）
- ✅ 事务（提交 / 回滚 / 嵌套 Savepoint / 跨实体共享连接）
- 软删除 `@SqlColumn(deleted = true)`
- 审计字段自动填充 `createdAt / updatedAt`
- 方言（MySQL / PostgreSQL / Oracle / 达梦）

### Stage 2 · 治理（约 1 周）
- 拦截器链（多租户、软删、全表拦截、慢 SQL 日志）
- SQL 指纹：同一模板不同参数归并统计，找出真正的高频慢查询
- lint + 快照测试进 CI

### Stage 3 · 生态（2–3 周）
- 从库反向生成语句骨架（`information_schema` → JSON）
- JSON → Java 常量/接口生成
- 配置中心热更新 + 版本灰度 + 一键回滚
- IDE 插件（已有 JSON Schema 基础）

### Stage 4 · 慎重
- 分库分表路由
- 读写分离
- 跨库 join（大概率不该做）

## 五、风险清单

1. **模板改动的影响面不可见。** 改一个 `findPage` 模板可能影响 50 张表，需要"谁 extends 了我"的反查能力，否则一次改动就是一次赌博。
2. **热更新 + 无版本 = 事故温床。** 版本、灰度、回滚三件套缺一不可，否则宁可重启发布。
3. **`ident` / `raw` 是唯一的拼接口，必须清单化。** 哪条语句用了、谁批准的、有没有 enum 兜底，要能一条命令查出来。
4. **反射映射有性能成本。** 当前 `mapRow` 每次 `setAccessible(true)`，高频查询要缓存 `Field`，否则 QPS 上万时会成为瓶颈（这是本项目最实在的一处待优化）。
5. **ThreadLocal + 连接池的坑。** 事务上下文绑定线程，异步/线程池复用会导致连接泄漏或串事务。要在文档里写明"事务块内不要切线程"。

## 六、天花板在哪

技术上它够得着"SQL 治理平台"：多租户、审计、灰度、监控、跨方言。这些都做得到。

**真正的天花板不在技术，在纪律。**

它要求团队把 SQL 当配置管理：编号连续、描述完整、改动评审、快照更新。纪律到位，它就是一套好用的 SQL 基础设施；纪律不到位，它退化成一个"换了个格式的 MyBatis XML"，还多了一层 JSON 的阅读成本。

**值不值得的判据：**

| 条件 | 建议 |
|---|---|
| SQL 条数 > 200，有多租户/多方言/审计需求，有人负责规范 | 值得，能显著降低"改一处炸一片"的风险 |
| 团队小、SQL 少于 50 条、只连一种库 | 直接用 MyBatis-Plus，省事得多 |
| 主要诉求是"SQL 要能被程序生成"（低代码、AI 生成） | 值得，这是它相对 XML 的核心优势 |

---

## 七、如果只做一件事

**做拦截器 + 软删除 + 多租户。**

理由：这三个加起来不到 300 行，但能干掉业务代码里最重复、最容易漏、最容易出安全事故的那部分逻辑——`WHERE tenant_id = ? AND deleted = 0` 每天手写几十遍，早晚漏一次。而漏一次的代价，可能比这套框架本身所有代码都贵。
